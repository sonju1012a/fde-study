# 데이터 프로파일링 (고객 데이터 첫날 진단)

FDE가 고객 데이터를 처음 받았을 때 하는 일을 한 번에 한다. 스크립트가 사실(숫자)을 뽑고, Claude가 그 사실을 "무슨 뜻인지, 고객에게 뭘 물어야 하는지"로 바꾼다. 둘을 섞지 않는다.

## 절차

1. **파일 확인.** 인자로 받은 경로가 있는지, 확장자가 csv/tsv/txt/json/jsonl 인지 본다. 엑셀(xlsx)은 지원하지 않으므로 CSV로 저장해 달라고 안내하고 멈춘다. 파일이 100MB를 넘으면 `--limit=50000`을 붙여 앞부분만 먼저 본다.
2. **실행.** 인자를 그대로 넘긴다. API 호출이 없으므로 비용과 키는 신경 쓰지 않아도 된다.
   ```bash
   cd app && pnpm data-profile $ARGUMENTS
   ```
   - 같은 구조의 JSON이 여러 개면 `--merge=이름` 으로 한 장에 합친다. 예: `pnpm data-profile ../data/ground-truth/*.json --merge=gt`
   - JSON 안의 배열(품목 목록 등)을 행으로 보려면 `--path=items` 를 붙인다. 헤더와 품목은 따로 두 번 돌린다.
   - 고객이 "이 컬럼이 키다"라고 했으면 `--key=A,B` 로 검증한다. 유일하지 않으면 그 자체가 첫 번째 발견이다.
   - 구분자를 잘못 잡아 열 개수가 이상하면 `--sep=tab` 또는 `--sep=;` 로 강제한다.
3. **보고서 읽기.** `app/output/profile/<이름>.md` 를 읽는다. 순서대로 본다.
   - 머리말: 행·열 수, 완전 중복 행, 키 후보. 키 후보가 없으면 고객에게 키 정의를 묻는 질문이 1순위다.
   - 이슈 요약: 높음 → 중간 → 낮음. 각 이슈에는 "왜 문제인지"가 이미 적혀 있으니 그대로 옮기지 말고 이 데이터 맥락에서 다시 판단한다.
   - 마스터 정합성: 코드 하나에 이름이 여러 개면 마스터가 바뀐 것인지 수기 입력인지 구분이 필요하다.
   - 컬럼 요약 표: 타입이 기대와 다른 컬럼(날짜인데 string, 금액인데 string, 코드인데 integer)을 찾는다. 이건 스크립트가 못 잡는 것이다.
4. **사람용 요약 작성.** 아래 형식으로 답한다. 보고서를 통째로 붙이지 않는다.
   - **한 줄 결론**: 이 데이터를 그대로 쓸 수 있는지, 정제가 필요한지, 고객 확인 없이는 진행이 안 되는지 셋 중 하나.
   - **구조**: 행·열, 키, 한 행이 무엇을 뜻하는지 (예: "견적 1건의 품목 1줄"). 키가 조합 키면 헤더 중복 구조임을 짚는다.
   - **반드시 처리할 것** (높음·중간 이슈 중 실제로 파이프라인에 영향 주는 것만, 최대 5개): 컬럼, 현상, 영향, 제안 처리. 표로.
   - **고객에게 물어볼 것** (최대 7개): 스크립트가 "확인 필요"라고 한 것 중 데이터만으로 답이 안 나오는 것. 질문은 예/아니오나 선택형으로 닫아서 쓴다. "사업자번호가 비어 있는 71건은 신규 협력사입니까, 아니면 내보내기 설정 문제입니까?" 처럼.
   - **무시해도 되는 것**: 낮음 이슈 중 자유 텍스트 형식 차이, 금액 극단값 같은 정상 현상. 한 줄씩.
5. **다음 단계 제안.** 이 데이터가 어디에 쓰일지(추출 정답셋, ERP 적재, 매핑 소스)에 따라 한 가지만 제안한다. 질문하지 않는다.

## 판단 기준 (스크립트가 못 하는 부분)

- **결측은 비율이 아니라 용도로 판단한다.** 비고 30% 결측은 정상이고, 사업자번호 30% 결측은 ERP 적재 시 거부된다. 컬럼 이름과 하류 시스템을 보고 결정한다.
- **형식 불일치는 "누가 입력했나"의 문제다.** 연락처에 전화와 이메일이 섞여 있으면 입력 화면에 필드가 하나뿐이었다는 뜻이다. 데이터 정제보다 원천 화면 수정을 제안할 수도 있다.
- **타입 혼재(숫자 자리에 "협의", "별도")는 비즈니스 규칙이다.** 지우지 말고 별도 플래그 컬럼으로 보존하라고 제안한다. 고객은 보통 그 값을 보고 싶어 한다.
- **극단값은 단위 혼용부터 의심한다.** 원/천원, EA/BOX, 개당/세트당. 중앙값의 1000배 이상 벌어질 때만 이슈로 올라오게 해 뒀다.
- **코드값 목록(20개 이하)은 전부 읽는다.** "EA, 대, SET"처럼 같은 뜻이 다른 표기로 있으면 정규화 매핑표를 바로 만들어 제안한다.
- **유일키 후보가 금액·타임스탬프면 키가 아니다.** 스크립트가 걸러내지만, 혹시 올라오면 무시한다.

## 주의

- 고객 데이터는 레포 밖에 둔다. `data/` 아래에 복사하지 않는다. 산출물(`app/output/profile/`)도 `.gitignore`에 걸려 있어 커밋되지 않는다.
- 개인정보(이름, 전화, 이메일, 사업자번호)가 있는 컬럼은 요약에 실제 값을 쓰지 않는다. 형식과 건수만 쓴다.
- 이 스킬은 진단만 한다. 정제·변환 스크립트는 고객이 질문에 답한 뒤에 만든다. 답 없이 "알아서" 고치면 나중에 되돌리기 어렵다.
- `scripts/profile.ts`는 외부 의존성이 없다. 고객 환경에 파일 하나만 복사해서 `node --import tsx scripts/profile.ts` 또는 `npx tsx profile.ts` 로 돌릴 수 있다.

## 예시

```bash
pnpm data-profile ../data/erp/erp_quote_export_2026Q3.csv --key=ERP견적번호,순번
pnpm data-profile ../data/ground-truth/*.json --merge=gt-header
pnpm data-profile ../data/ground-truth/*.json --path=items --merge=gt-items
```

첫 번째 예시에서 나와야 할 결론: "견적 50건 × 품목 249줄의 헤더 중복 구조, 키는 ERP견적번호+순번. 연락처 컬럼에 전화·이메일 혼재, 규격 9건이 숫자로 저장됨, 단위 코드 EA/대/SET 혼용. 사업자번호 28% 결측은 신규 협력사인지 확인 필요."
