# 케이스 스터디: 협력사 견적서 수기 입력을 AI 검토 워크플로로 바꾸기

> 가상의 고객사를 설정하고 Forward Deployed Engineer의 업무 흐름(문제 발굴 → 범위 합의 → 프로토타입 → 평가 → 인수)을 처음부터 끝까지 재현한 프로젝트입니다.
> 고객사, 협력사, 견적서는 전부 가상이며 데이터는 생성기로 만들었습니다. 그 외 설계 판단, 코드, 평가 과정은 실제로 수행한 것입니다.

## 한 줄 요약

월 300~500건의 협력사 견적서 PDF를 손으로 ERP에 입력하던 구매팀에, **AI가 초안을 뽑고 사람이 검토·확정하는 워크플로**를 만들어 50건 기준 필드 정확도 99.9%, 수정 없이 통과 98%를 달성했다. 더 중요한 성과는 첫 평가에서 나온 64%라는 숫자가 모델 오류가 아니라 **정답 데이터의 오류**였음을 밝혀낸 과정이다.

## 1. 배경과 문제

**고객**: 한빛산업(가상). 산업용 기계 부품 유통, 직원 250명, 구매팀 6명. 자체 ERP(설치형), 사내 개발 인력 없음.

**고객이 처음 말한 요청**
> "협력사에서 오는 견적서를 ERP에 일일이 손으로 입력하는데, 이걸 AI로 자동화할 수 없나요?"

**첫 미팅에서 파악한 실제 상황**
- 협력사 80곳에서 월 300~500건의 견적서가 이메일 첨부 PDF로 들어온다. 양식은 제각각.
- 대리 2명이 번갈아 ERP에 입력한다. 주당 약 2인일.
- 지난달 수량을 잘못 입력해 발주가 10배로 나간 사고가 있었다. 경영진이 민감해진 계기.

**진짜 문제**
고객은 "자동 입력"을 말했지만 고통은 두 가지였다. 반복 입력에 쓰는 시간, 그리고 **입력 오류가 발주 사고로 이어지는 불안**. 두 번째가 더 컸다. 그래서 완전 자동화가 아니라 "AI가 초안을 뽑고 사람이 빠르게 검토·확정하는 구조"로 방향을 잡았다. 이 판단이 프로젝트 전체의 뼈대가 됐다.

## 2. 범위를 정하기까지

2차 인터뷰에서 샘플 50건, ERP 입력값, 입력 화면 스크린샷을 받았다. 그 과정에서 범위가 구체화됐다.

| 논점 | 결정 | 이유 |
|---|---|---|
| ERP 직접 자동입력 | 2차로 미룸. 1차는 CSV + 품목 그리드 붙여넣기 텍스트 | ERP가 설치형이고 외부 계정 발급이 보안 승인 사항. 벤더 API 여부 미확인 |
| 스캔본 (전체의 약 10%) | 1차 정확도 목표에서 제외 | 텍스트 PDF로 먼저 검증하고 확대 |
| USD 견적 | 원문 통화로 추출, 환산은 구글 시트 GOOGLEFINANCE 수식으로 | 고객은 발주일 환율로 환산하므로 추출 시점에 고정하면 틀린 값이 됨. 고객이 이미 쓰는 도구라 추가 비용 없음 |
| 유효기간 "견적일로부터 30일" | 상대 표현으로 추출하고 CSV 변환 단계에서 날짜 계산 | ERP는 날짜만 받음. 대리들이 지금 손으로 하는 계산과 동일 |
| 정답 데이터 | 고객 ERP 입력값을 쓰되 검증 후 사용 | 고객이 "사람이 넣은 거라 틀린 데가 있다"고 명시 |

FDE 관점에서 가장 중요한 결정은 **"자동입력까지 해드리겠다"는 제안을 스스로 접은 것**이다. 웹 ERP면 계정 하나로 가능하다고 제안했지만, 설치형 ERP와 보안 정책이라는 현실 앞에서 1차 범위를 지키는 게 맞았다. 범위를 넓혀 실패하는 것보다 좁혀서 인수받는 게 신뢰를 만든다.

## 3. 접근

### 아키텍처

```
PDF ──▶ Claude (구조화 출력) ──▶ 코드 검산 ──▶ 검토 UI ──▶ 확정 ──▶ CSV / ERP 붙여넣기 텍스트
                                     │                               │
                                     └── 경고 (수량×단가, 합계 불일치) ──┘
                                                                     └──▶ 수정 이력 → 통계 (피드백 루프)
```

### 설계 원칙 세 가지

**모델은 읽고, 코드는 계산한다.**
모델에게 "금액을 계산하지 말고 적힌 대로 옮겨라"고 지시하고, 수량×단가, 품목 합=공급가액, 부가세 10%, 합계 검산은 코드가 한다. 이러면 불일치가 났을 때 "모델이 잘못 읽은 것"과 "문서 자체가 틀린 것"을 구분할 수 있다. 발주 사고 방지는 모델의 확률적 판단이 아니라 코드가 보장해야 하는 부분이다.

**스키마가 계약이다.**
Zod 스키마 하나가 모델 출력 제약(structured output), TypeScript 타입, 정답 데이터 구조, CSV 변환 입력을 모두 통일한다. 평가 스크립트와 검토 UI도 같은 스키마를 쓴다. 필드를 하나 추가하면 전 구간에 타입 오류로 드러난다.

**모델이 자신 없는 곳을 스스로 말하게 한다.**
`low_confidence_fields`를 출력에 포함시켜, 모델이 애매하게 읽은 필드를 표시하게 했다. 검토 화면은 이 필드와 검산 경고를 노란색으로 강조한다. 실제로 50건 중 유일하게 틀린 필드(회사 대표번호를 담당자 번호로 읽은 것)는 모델이 미리 "자신 없음"으로 표시한 항목이었다.

### 기술 스택

Next.js 16 + TypeScript + Tailwind, Anthropic SDK(Claude Opus 5, structured outputs), Zod. 검토 상태는 프로토타입이라 localStorage에 두고 저장소 인터페이스만 분리했다. 데이터 생성기, 추출, 평가, 데이터 동기화는 전부 Node 스크립트.

## 4. 결과

### 정확도 (샘플 50건, 품목 250라인)

| 지표 | 값 |
|---|---|
| 수정 없이 통과한 건 | 49/50 (98.0%) |
| 헤더 필드 정확도 (16개 필드 × 50건) | 99.9% |
| 품목 필드 정확도 (6개 필드 × 250라인) | 100% |
| 검산 경고 | 0건 |

### 비용 추정

건당 입력 약 4,500토큰, 출력 약 1,500토큰으로 Claude Opus 5 기준 약 $0.06. 월 500건이면 약 $30, 원화로 4만 원대. 현재 투입되는 월 8인일 인건비의 3~4% 수준. (API 실측이 아닌 추정값. 아래 한계 참조)

### 산출물

- 추출 파이프라인과 50건 일괄 실행기, 정확도 평가 스크립트
- ERP 내보내기와 같은 컬럼 구조의 CSV, 구글 시트용 환율 수식 버전, 품목 그리드 붙여넣기 텍스트
- 검토 UI: 목록 / 원본 대조 검토 / 수정 통계
- 요구사항 문서, 결정 기록, 평가 리포트

## 5. 평가 과정에서 배운 것: 64%에서 98%로

첫 평가 결과는 **64%(32/50)** 였다. 불일치 85건을 하나씩 뜯어보니:

| 원인 | 건수 | 실제로는 |
|---|---|---|
| 공문형·간이형 양식에는 "단위" 열이 없는데 정답 데이터에 단위가 들어 있었음 | 80 | 문서에 없는 정보를 정답으로 요구한 것. 추출은 올바르게 null을 냄 |
| 비고에 "VAT 별도" 등 문서에 실제로 있는 문구를 추가로 포함 | 4 | 틀린 게 아님. 자유 텍스트를 완전 일치로 비교한 평가 기준이 문제 |
| 회사 대표번호를 담당자 번호로 읽음 | 1 | 진짜 불일치. 모델이 스스로 "자신 없음" 표시 |

정답 데이터 생성 규칙과 평가 기준을 고치고 다시 돌려서 98%가 됐다.

여기서 얻은 교훈은 실제 고객 프로젝트에 그대로 적용된다. 고객이 준 "정답"(ERP 입력값)에는 사람의 입력 오류가 섞여 있다고 고객 스스로 말했다. **정확도 숫자를 보고 바로 "모델이 틀렸다"고 하면 안 된다.** 불일치는 추출 오류, 정답 오류, 평가 기준 오류 세 가지가 섞여 있고, 고객 데이터와 비교하기 전에 평가 기준부터 검증해야 한다. 그리고 그 과정에서 찾아낸 "정답 데이터의 오류"는 고객에게 보여줄 첫 번째 성과가 된다. "이 시스템이 이미 ERP에 들어간 오류를 찾아냈습니다"는 어떤 정확도 숫자보다 설득력이 있다.

## 6. 의도적으로 미룬 결정

- **검토 상태를 localStorage에 저장.** 프로토타입 단계에서 DB를 붙이면 배포와 데모가 무거워진다. 저장소 인터페이스를 분리해 두고 운영 전환 시 교체한다.
- **환율을 GOOGLEFINANCE로.** 회계 기준인 서울외국환중개 매매기준율과 소폭 차이가 날 수 있다. 고객 회계팀 확인이 필요한 항목으로 남겨 두었고, 검토자가 덮어쓸 수 있게 했다.
- **스캔본 미포함.** 고객이 두 번 물었지만 1차에서는 텍스트 PDF로 검증 범위를 좁혔다. 어려운 샘플(스캔, 2페이지, 변칙 표)을 추가하면 정확도가 떨어질 것이고, 그때부터가 2차 개선 작업이다.

## 7. 다음 단계

1. 어려운 샘플 20~30건 추가(스캔본, 다중 페이지, 할인 행, 협력사 계산 오류)로 평가셋 강화
2. 검산 실패 시 경고를 붙여 자동 재추출, 협력사 마스터 데이터와 사업자번호·담당자 대조
3. 검토자 수정 이력을 주간 단위로 분석해 프롬프트 규칙과 평가셋에 반영하는 운영 루프
4. API 전환 후 실측 비용·시간 확보, Vercel 배포

## 8. 이 프로젝트의 한계 (정직하게)

- 고객과 데이터가 가상이다. 요구사항 발굴은 역할극으로 했고, 견적서는 생성기로 만든 것이라 실제 문서보다 깨끗하다.
- 추출 자체는 API 키 없이 Claude Code가 PDF를 직접 읽는 방식으로 수행했다. 파이프라인 코드와 프롬프트는 API용으로 작성돼 있고 실행 가능하지만, 정확도와 비용 수치는 Claude Opus 5 API의 실측이 아니다.
- 50건은 통계적으로 작은 수다. 98%는 "이 양식 5종에서는 잘 된다"는 뜻이지 일반 성능이 아니다.
