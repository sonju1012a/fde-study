# 03. 1차 추출 평가 결과

## 실행 조건

- 대상: 고객 제공 샘플 50건 (`data/samples/`)
- 추출 엔진: **Claude Code가 PDF를 직접 읽어 스키마대로 작성** (API 키 없이 진행). 프롬프트 규칙은 `app/src/lib/extract.ts`의 시스템 프롬프트와 동일.
  - 따라서 비용·소요시간은 실측값이 아님. API 전환 후 `FORCE=1 pnpm extract`로 재측정 필요.
- 정답: `data/ground-truth/` (문서 생성 시 함께 만든 값)
- 평가 스크립트: `app/scripts/eval.ts` → `app/output/eval-report.md`

유일한 불일치: Q033 담당자 전화번호. 문서 상단 회사 대표번호(02-561-7000)를 담당자 번호로 읽음. 추출 시 `low_confidence_fields`에 스스로 표시한 항목이라 검토 화면에서 강조 표시될 건이었음.

## 평가 과정에서 발견한 것 (중요)

첫 실행 결과는 **64%(32/50)** 였다. 불일치 85건을 뜯어보니 추출 오류가 아니라 **평가 기준의 오류**가 대부분이었다.

| 원인 | 건수 | 판단 | 조치 |
|---|---|---|---|
| 공문형·간이형 양식에는 "단위" 열이 없는데 정답 데이터에는 단위가 들어 있었음 | 80 | 문서에 없는 정보를 정답으로 요구한 것. 추출은 맞게 null을 냄 | 정답 데이터 생성 규칙 수정: 단위 열이 없는 양식은 정답도 null |
| 비고(note)에 "VAT 별도", 환율 문구를 함께 넣음 | 4 | 문서에 실제로 있는 문구라 틀린 게 아님. 비고는 자유 텍스트라 완전 일치 비교가 부적절 | 평가 기준을 "정답 문구가 추출값에 포함되면 정답"으로 완화 |
| 회사 대표번호를 담당자 번호로 읽음 | 1 | 문서 자체가 모호. 진짜 불일치로 유지 | 프롬프트에 "회사 헤더의 대표번호와 담당자 번호 구분" 규칙 추가 검토 |

**교훈:** 정확도 숫자를 보고 바로 "모델이 틀렸다"고 하면 안 된다. 불일치는 세 종류가 섞여 있다.

1. 추출이 틀린 것
2. 정답 데이터가 틀리거나 문서에 없는 정보를 요구한 것
3. 평가 기준이 너무 엄격한 것 (자유 텍스트의 완전 일치 등)

실제 고객 프로젝트에서는 2번이 특히 흔하다. 고객이 준 ERP 입력값에도 사람 입력 오류가 섞여 있다고 고객 스스로 말했다. **고객 데이터와 비교하기 전에 평가 기준부터 검증하는 단계**가 필요하고, 이 단계에서 찾은 "정답 데이터의 오류"는 그 자체로 고객에게 보여줄 가치가 있는 발견이다.
